# 온라인 텍사스 홀덤

친구들끼리 방 코드로 모여 플레이하는 프라이빗 홀덤 웹 게임.
[PROMPT.md](PROMPT.md)의 설계 문서를 구현한 것입니다.

## 실행

```bash
npm install
npm run dev     # 서버(:3001) + 클라이언트(:5173) 동시 실행
```

`http://localhost:5173` 접속 → 닉네임 입력 → **게임 방식 선택** → **새 방 만들기**
→ 방 코드를 친구에게 전달. 2명 이상 모이면 방장이 **게임 시작**을 누릅니다.
이후 핸드는 6초 뒤 자동으로 이어집니다. 최대 9명.

```bash
npm test        # 서버 테스트 82개
npm run typecheck
npm run build   # 클라이언트 프로덕션 빌드 → client/dist
npm start       # 빌드된 클라이언트까지 서버 하나로 서빙 (:3001)
```

친구들이 접속하려면 서버가 외부에서 닿아야 합니다. 아래 [배포](#배포)를 보세요.

## 배포

### 먼저 알아둘 제약

- **서버는 반드시 1대여야 합니다.** 방·칩·시계가 전부 프로세스 메모리에 있습니다.
  오토스케일이나 다중 인스턴스를 켜면 같은 방 사람들이 서로 다른 서버에 붙어 게임이 깨집니다.
  (여러 대로 늘리려면 Redis 어댑터 + 방 상태 외부 저장이 필요합니다.)
- **서버를 재시작하면 진행 중인 게임이 사라집니다.** 자동 슬립이 특히 위험합니다 —
  놀고 있으면 잠드는 플랜에서는 화장실 다녀오는 사이 판이 날아갑니다.
  Vercel 같은 서버리스 플랫폼은 이 앱에 맞지 않습니다(연결이 최대 5분에 끊기고,
  같은 방 사람들이 서로 다른 인스턴스로 갈립니다).
- **WebSocket을 지원하는 호스트여야 합니다.** 클라이언트가 `transports: ["websocket"]`로
  폴백 없이 붙습니다. WebSocket이 막힌 환경까지 감당하려면
  [useSocket.ts](client/src/hooks/useSocket.ts)에서 `["websocket", "polling"]`으로 바꾸세요.

### 환경변수

| 어디 | 변수 | 값 | 언제 쓰이나 |
|---|---|---|---|
| 서버 | `PORT` | 호스트가 자동 주입 | 미지정 시 3001 |
| 서버 | `CLIENT_ORIGIN` | 클라이언트 주소 | 방법 B에서만 필요. CORS 허용 출처 |
| 클라이언트 | `VITE_SERVER_URL` | 서버 주소 | 방법 B에서만 필요. **빌드 시점에 코드로 박힙니다** |

### 방법 A — 한 서비스로 배포 (권장, 구현되어 있음)

서버가 `client/dist`를 함께 서빙합니다. 주소가 하나라 CORS도, 서로의 URL을 먼저
알아야 하는 순환 문제도 없습니다. **환경변수 없이 그대로 배포됩니다.**

| 항목 | 값 |
|---|---|
| Build | `npm install && npm run build` |
| Start | `npm start` |
| 환경변수 | 없음 (`PORT`는 호스트가 자동 주입) |
| 인스턴스 수 | **1** 고정 |

동작 방식:

- [server.ts](server/src/server.ts)가 `client/dist/index.html`이 있으면 정적 서빙과
  SPA 폴백을 붙입니다. 없으면(개발 중) 아무것도 하지 않고 클라이언트는 Vite가 띄웁니다.
- [useSocket.ts](client/src/hooks/useSocket.ts)의 배포 빌드는 `window.location.origin`에
  접속합니다. 그래서 어떤 도메인에 올리든 다시 빌드할 필요가 없습니다.
- `/socket.io/*`는 engine.io가 Express보다 먼저 가로채므로 SPA 폴백에 걸리지 않습니다.
  ([server.test.ts](server/src/server.test.ts)가 이걸 검증합니다.)

### 방법 B — 서버와 클라이언트를 따로 배포

클라이언트를 정적 호스팅(Vercel/Netlify 등)에 따로 올리고 싶을 때만 쓰세요.
**서버를 먼저 띄워 주소를 확보한 뒤** 클라이언트를 빌드해야 합니다.

1. **서버**: Build `npm install`, Start `npm start -w server`, 인스턴스 1개
2. 서버 주소 확보 → `https://holdem-api.example.com`
3. **클라이언트**: Build `npm install && npm run build -w client`,
   Publish directory `client/dist`,
   환경변수 `VITE_SERVER_URL=https://holdem-api.example.com`
4. 클라이언트 주소를 서버의 `CLIENT_ORIGIN`에 넣고 서버 재배포

### Fly.io로 배포하기

[Dockerfile](Dockerfile)과 [fly.toml](fly.toml)이 준비되어 있습니다. 그대로 쓰면 됩니다.

```bash
# 1. flyctl 설치 (macOS)
brew install flyctl

# 2. 로그인 (브라우저가 열립니다)
fly auth login

# 3. 앱 이름을 정합니다. Fly 전체에서 고유해야 하므로 아무도 안 쓸 이름으로.
fly apps create holdem-우리모임

# 4. fly.toml의 app 이름을 방금 만든 이름으로 바꿉니다
#    app = "holdem"  →  app = "holdem-우리모임"

# 5. 배포
fly deploy

# 6. 머신이 정확히 1대인지 확인 (중요 — 아래 설명 참고)
fly scale count 1

# 7. 열어보기
fly open
```

배포가 끝나면 `https://holdem-우리모임.fly.dev` 주소가 나옵니다. 이 주소를 친구들에게
보내면 됩니다. 환경변수 설정은 필요 없습니다.

#### 확인

```bash
curl https://<앱이름>.fly.dev/health     # {"ok":true,"rooms":0}
fly logs                                  # 실시간 로그
fly status                                # 머신 상태 (1대여야 정상)
```

#### fly.toml에서 절대 건드리면 안 되는 것

```toml
auto_stop_machines = "off"    # "stop"이면 잠깐 자리를 비울 때 판이 날아간다
min_machines_running = 1
```

Fly의 기본값은 트래픽이 없을 때 머신을 멈추는 것입니다. 이 앱은 방·칩·블라인드
시계가 전부 프로세스 메모리에 있어서, 머신이 멈추면 진행 중인 게임이 사라집니다.
같은 이유로 **머신을 2대 이상으로 늘리면 안 됩니다** — 같은 방 사람들이 서로 다른
머신에 붙어 "그런 방이 없습니다"가 뜹니다.

#### 리전

`primary_region = "nrt"`(도쿄)로 잡혀 있습니다. Fly에 서울 리전은 없고 도쿄가 한국에서
가장 가깝습니다. 다른 곳에서 모인다면 `fly platform regions`로 목록을 보고 바꾸세요.

#### 비용

Fly는 무료 티어가 없습니다. 이 설정(shared-cpu-1x / 512MB)은 **월 3~4달러** 수준이고,
신규 계정에는 체험 크레딧이 있습니다. 안 쓸 때 `fly scale count 0`으로 내려두면
과금이 멈춥니다(진행 중인 게임은 사라집니다).

#### 업데이트

```bash
fly deploy      # 코드를 고친 뒤 다시 배포
```

배포하면 머신이 재시작되므로 진행 중인 판이 사라집니다. 게임 중에는 배포하지 마세요.

### 배포 후 점검

```bash
curl https://<배포주소>/health          # {"ok":true,"rooms":0}
curl -I https://<배포주소>/             # 200, content-type: text/html
```

그다음 브라우저 두 개(하나는 시크릿 창)로 접속해 방을 만들고 입장해 보세요.
시크릿 창을 쓰는 이유는 `playerId`가 localStorage에 저장돼서, 같은 브라우저의
새 탭은 같은 사람으로 인식되기 때문입니다.

콘솔에 `WebSocket connection failed`가 뜨면 호스트가 WebSocket 업그레이드를
막고 있는 것이고, `CORS` 오류가 뜨면 서버의 `CLIENT_ORIGIN`이 실제 클라이언트
주소와 다른 것입니다.

## 구조

```
shared/types.ts     # 서버·클라이언트가 함께 쓰는 프로토콜 타입 (단일 계약)
server/src/game/    # deck, betting(사이드팟), handEvaluator, tournament(블라인드 구조),
                    # room(상태 머신), roomManager
server/src/socket/  # 소켓 이벤트 핸들러
client/src/         # React UI + 연출
```

**서버가 유일한 진실 공급원입니다.** 셔플·베팅·판정은 전부 서버에서 하고,
클라이언트는 받은 상태를 렌더링만 합니다.

남의 홀카드는 [`Room.toPublicState()`](server/src/game/room.ts) 한 곳에서만 마스킹합니다.
마스킹 지점이 하나여야 새는 경로가 생기지 않습니다.
소켓 통합 테스트가 쇼다운 전까지 오간 **모든** 상태 메시지에 남의 카드가 없음을 검증합니다.

## 게임 방식

방을 만들 때 두 가지 중 하나를 고릅니다.

### 토너먼트
| | |
|---|---|
| 스타팅칩 | 300만 |
| 리바인 | 400만 (최초 참가 포함 **총 3회**, 즉 리바인 2회) |
| 블라인드 | 10분마다 상승 |
| 브레이크 | 50분 진행 후 10분 |
| 종료 | 한 명 남을 때까지 |

| 레벨 | 스몰 | 빅 | 앤티 |
|---|---|---|---|
| 1 | 1만 | 2만 | — |
| 2 | 2만 | 4만 | — |
| 3 | 3만 | 6만 | 6만 |
| 4 | 4만 | 8만 | 8만 |
| 5 | 5만 | 10만 | 10만 |
| 6 | 10만 | 20만 | 20만 |
| 7+ | 이전 레벨의 2배씩 | | |

레벨 1~5가 정확히 50분이므로 브레이크는 레벨 5가 끝난 직후에 옵니다.
브레이크가 끝나면 레벨 6부터 자동으로 재개됩니다.

### 타임어택
| | |
|---|---|
| 스타팅칩 | 500만 |
| 리바인 | 500만 (최초 참가 포함 **총 4회**, 즉 리바인 3회) |
| 블라인드 | 10만/10만으로 40분 → 50만/50만으로 10분 |
| 종료 | 50분 뒤 칩이 많은 순으로 순위 |

### 앤티와 리바인
- **앤티는 빅블라인드가 대표로 냅니다**(빅블라인드 앤티). 표에서 앤티 금액이 항상
  빅블라인드와 같은 것과 일치합니다. 앤티는 누구의 베팅도 아닌 데드머니라
  사이드팟 층을 만들지 않고 메인팟에 얹힙니다.
- **리바인은 칩이 0이 됐을 때만** 가능하고, 진행 중인 핸드가 끝난 뒤에 할 수 있습니다.
  횟수를 다 쓰고 칩이 0이 되면 탈락합니다.
- 블라인드 상승은 핸드 도중에 적용되지 않고 **다음 핸드부터** 반영됩니다.

## 설계 문서와 달라진 점

| 항목 | 문서 | 구현 | 이유 |
|---|---|---|---|
| 액션 | call/raise/fold/allin | **check 추가** | 없으면 포스트플랍 첫 액션과 프리플랍 BB 옵션을 표현할 수 없음 |
| 사이드팟 | MVP는 "올인 1명" 단순화 제안 | **일반형 구현** | 약 30줄이고, 나중에 고치면 팟 분배 전체를 다시 건드려야 함 |
| 셔플 난수 | `Math.random` | `crypto.randomInt` | 모듈로 편향이 없음. 한 줄 차이 |
| 서버 실행 | tsc 빌드 | `tsx`로 직접 실행 | `shared/`를 두 워크스페이스가 함께 쓰는데 outDir 경로가 꼬임. 타입 검증은 `tsc --noEmit`으로 별도 수행 |

문서 8장 2번(민레이즈)은 이미 그대로 구현되어 있었고, 문서의 예시(1만/2만에서
4만으로 레이즈 → 다음은 6만부터)를 테스트로 고정해 두었습니다.

## 구현된 규칙

- 블라인드, 헤즈업 예외(딜러가 SB이며 프리플랍 선행), UTG/포스트플랍 액션 순서
- 최소 레이즈 강제. **최소액에 못 미치는 올인은 베팅을 다시 열지 않습니다**(콜만 가능)
- 스택이 콜 금액보다 적으면 올인이 레이즈가 아니라 콜로 처리됩니다
- 일반형 사이드팟, 동점 분할, 나머지 칩은 딜러 왼쪽부터
- 액션 가능한 사람이 1명 이하가 되면 남은 보드를 자동으로 깔고 쇼다운
- 빅블라인드 앤티, 레벨별 블라인드 상승, 브레이크타임
- 리바인과 탈락, 최종 순위 산정(칩 순 · 동률이면 나중에 탈락한 사람이 위)
- 45초 턴 타임아웃 → 자동 체크/폴드
- 접속이 끊겨도 핸드 중에는 좌석과 칩이 유지되고, 같은 브라우저로 돌아오면 복귀합니다
- 빈 방은 2분간 유지됩니다 (방장이 새로고침해도 코드가 죽지 않도록)

## 연출

- **셔플**: 새 핸드마다 카드 뒷면 9장이 리플되는 오버레이. 실제 셔플 결과와 무관한 순수 연출
- **딜링**: 덱에서 각 좌석으로 stagger 이동. 자기 카드만 `rotateY` 3D 플립으로 뒤집힘
- **칩 이동**: 베팅 라운드가 끝나 정산되는 순간 좌석 → 팟으로 칩이 날아감
- **좌석**: 타원 위에 각도 계산으로 배치하고 **자기 자리를 항상 화면 아래**로 회전
- 테이블은 960×600 고정 좌표로 그린 뒤 화면에 맞춰 통째로 스케일합니다.
  애니메이션의 시작·끝점을 픽셀로 정확히 잡기 위해서입니다.

## 알려진 제약

- 방 상태는 메모리에만 있습니다. 서버를 재시작하면 진행 중인 게임이 사라집니다
  (클라이언트는 이를 감지해 로비로 돌아갑니다)
- 사운드는 넣지 않았습니다 (음원 에셋 필요)
- 채팅 없음. 로그 패널만 있습니다
- 블라인드 레벨 시계는 서버 프로세스 기준입니다. 서버가 재시작되면 시계도 초기화됩니다
